# Data contract

Schema versions `1.0.0` and `1.1.0` use JSON Schema Draft 2020-12. The original `1.0.0` example remains valid; Phase 1 reports use `1.1.0`, adding required `pe_facts` and optional `comparison`. `schemas/report-v1.schema.json` checks required fields, primitive types, and enums. Python constructors, `validate_references`, and `validate_payload_references` check relationships and invariants that JSON Schema cannot express conveniently. Consumers of external JSON must run **both** schema and payload semantic checks; no JSON ingestion API is provided yet.

`Artifact` has a stable ID, SHA-256, byte count, format label, and optional safe origin label. No absolute user path is emitted. `Evidence` points to an artifact, records parser source and extraction method, and may have an offset, RVA, VA, header field, byte range, or instruction range. Ranges are half-open `[start, end)` and must have `end > start`. `verified` requires a recorded location; Phase 1 generated verified evidence has an in-bounds raw byte range and a hex excerpt capped at 32 bytes. `unresolved` cannot claim a location; `pending` is retained for older reports. A verified range proves provenance of the extracted/derived field to those bytes, not that a second parser agreed with its meaning.

`pe_facts` stores machine-readable `path`, scalar `value`, `evidence_id`, and optional `note`, sorted by path. The corresponding observation states that field's value. Every fact has one evidence link. If no raw location is defensible, evidence is `unresolved` and confidence `unknown`; zero is never used as a substitute offset. Certificate directory addresses are file offsets, while other directory addresses are RVAs. A candidate overlay is a layout observation with a stated limitation. A raw COFF timestamp is reported without calling it a trusted build time.

`Observation` states an extracted fact and references one or more evidence IDs. It must not claim runtime behavior from a static import. `Inference` states a possible interpretation, references observations, and separately records strength, alternative explanations, and limitations. `Disagreement` records parser divergence as `equivalent`, `semantic_difference`, `unsupported`, `malformed_input`, or `suspected_parser_defect`; divergence is not automatically a defect. `Limitation` and `Issue` are structured for CLI and future UI use.

Qualitative levels are `high`, `medium`, `low`, `unknown`. `observation_confidence` concerns extraction reliability; `inference_strength` concerns how strongly observations support an interpretation. Neither is a probability of malware or proof of runtime activity.

Entity IDs use letters followed by up to 127 ASCII letters, digits, `.`, `_`, `:`, or `-`. IDs are unique across the report. An inference must resolve to observations, each observation to evidence, and each evidence to the report artifact. A limitation subject may point to any entity. Schema shape alone does not enforce these links; Python semantic validation does.

Canonical serialization sorts object keys and entity arrays by ID, `pe_facts` by path, and warnings/errors by code then message. It uses UTF-8 compatible JSON text, compact separators, a trailing newline, and rejects NaN/Infinity. It contains no nondeterministic timestamp, host name, or absolute path. `parser_versions` records only parsers actually run. Differential `comparison` counts equivalent normalized fields and disagreements; each disagreement has a field path, both values, category, explanation, limitations, and primary evidence when available. Reference locations are not independently verified by comparison. Future environment diagnostics must live outside the canonical analysis payload.
